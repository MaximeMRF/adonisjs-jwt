# Upgrading to 1.0

Version 1.0 hardens the security defaults and stabilizes the public API. Most applications only need to check the points below and update a few lines of configuration.

```sh
npm i @maximemrf/adonisjs-jwt@^1.0.0
```

`@adonisjs/auth` is now a peer dependency. It is already installed if you use the guard.

## Breaking changes

### Signing key derived from the application key

Without `secret`, tokens were signed with the raw application key. They are now signed with a key derived from it, see [Security](/guide/security#signing-key).

- **Access tokens issued by 0.9 are rejected** after the upgrade. Clients get a `401` and must refresh their token or log in again. Refresh tokens are stored in the database and **stay valid**, so clients with a refresh token don't have to log in again.
- The application key must be at least 32 characters, otherwise the guard throws at startup. AdonisJS generates 32 characters keys by default.

Applications that set `secret` are not affected.

### Access tokens expire after 1 hour by default

Without `tokenExpiresIn`, access tokens never expired. They now expire after `1h`. Set `tokenExpiresIn` to keep another lifetime.

A `content` function that sets `exp` itself now throws when issuing a token: remove `exp` and use `tokenExpiresIn`.

### JWKS requires issuer and audience

In JWKS mode, the guard throws at startup if `issuer` is missing, or if neither `audience` nor `verifyPayload` is set. Set them to the values of your identity provider, see [JWKS](/guide/jwks). If your provider's tokens have no `aud` claim specific to your API (Amazon Cognito access tokens, for example), check the claim that identifies your API with [`verifyPayload`](/guide/jwks#check-other-claims) instead of `audience`.

### Refresh token in the query string

A refresh token sent in the query string (`?refreshToken=…`) is ignored. Send it in the request body, a cookie or the `Authorization` header.

### Refresh token body field follows refreshTokenName

The refresh token was always read from the `refreshToken` body field. It is now read from the field named after `refreshTokenName`. If you set a custom `refreshTokenName` and your clients send the token in a `refreshToken` field, rename the field in your clients.

### Token lookup order

- **Refresh token**: when `useCookiesForRefreshToken` is enabled, the cookie is read before the request body.
- **Access token**: the `Authorization` header is read before the cookie, and the cookie is only read when `useCookies` is enabled. If you set the `token` cookie yourself without `useCookies`, enable `useCookies`.

See [Cookies and token transport](/guide/token-transport).

### JwtGuardOptions.expiresIn renamed to tokenExpiresIn

This only affects code that instantiates `JwtGuard` directly:

```ts
new JwtGuard(ctx, userProvider, {
  expiresIn: '1h', // [!code --]
  tokenExpiresIn: '1h', // [!code ++]
})
```

The `jwtGuard()` option was already named `tokenExpiresIn`.

## Other changes

These changes don't require any action.

- **Imports**: import from the main entrypoint. The old path still works.

  ```ts
  import { jwtGuard } from '@maximemrf/adonisjs-jwt/jwt_config' // [!code --]
  import { jwtGuard } from '@maximemrf/adonisjs-jwt' // [!code ++]
  ```

- **Typed `content`**: `user.getOriginal()` is typed after your model, the generic signature and the cast are no longer needed.

  ```ts
  content: <T>(user: JwtGuardUser<T>) => ({ // [!code --]
    email: (user.getOriginal() as User).email, // [!code --]
  content: (user) => ({ // [!code ++]
    email: user.getOriginal().email, // [!code ++]
    userId: user.getId(),
  }),
  ```

- **AdonisJS v7 apps without `secret`**: the guard now reads `APP_KEY` from the environment when `config/app.ts` has no `appKey`, which is the case of new AdonisJS v7 apps.
- **`node ace configure`** now adds the guard to `config/auth.ts` and the `refreshTokens` provider to the user model, see [Installation](/guide/installation).
- **JWKS defaults**: key fetches are cached and rate limited by default, see [Key fetching](/guide/jwks#key-fetching).
- **`revoke()`** also clears the access and refresh token cookies.
- **`refreshTokenAbilities`** are now checked by `generateWithRefreshToken()`.
- **`user.currentToken`** holds the new access token after `generateWithRefreshToken()`, which no longer returns `undefined` in its type.
- **Concurrent refreshes**: when two requests use the same refresh token, the one that fails no longer leaves the guard authenticated.
